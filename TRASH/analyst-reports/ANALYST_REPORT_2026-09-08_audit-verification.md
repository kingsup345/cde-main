## 1. ⚠️ `calculateEMA` — באג seeding בליבה (לא רק Bybit)

### מה שנטען
> "`calculateEMA` מאותחל מהקלוז הראשון, כך ש-EMA200 על 200 נרות עדיין בתהליך
> התכנסות."

### מה שקורה בפועל

`packages/engine/src/services/tradeEngine.ts:112-130`:

```ts
export function calculateEMA(values: number[], period: number): number[] {
  const k = 2 / (period + 1);
  const ema: number[] = [];
  let sum = 0;
  const initialCount = Math.min(period, values.length);
  for (let i = 0; i < initialCount; i++) sum += values[i];
  ema.push(sum / initialCount);              // ← נכתב באינדקס 0
  for (let i = 1; i < values.length; i++)    // ← הרקורסיה מתחילה מ-1
    ema.push(values[i] * k + ema[i - 1] * (1 - k));
  return ema;
}
```

**האתחול הוא SMA, לא "הקלוז הראשון"** — אז החלק הזה של הטענה שגוי. אבל ה-SMA
נכתב באינדקס **0** במקום באינדקס `period − 1`, והרקורסיה רצה מ-`i = 1`. מכאן
שתי תוצאות:

1. **אין אזור warmup.** הסדרה מוחזרת באורך מלא ללא `NaN`, כך שקורא לא יכול
   להבחין בין ערך מכונס לערך שאינו. `ema[5]` עבור period=200 מוצג כ-EMA200 תקין.
2. **ערך אינדקס 0 מכיל מידע מאינדקסים 1..period−1** — עתידיים ביחס אליו.
   עבור `emaLast` (רק האיבר האחרון) כל הקלט ממילא בחלון ההחלטה, ולכן **אין**
   look-ahead מעבר לנתון הזמין. אבל כל צרכן שסורק את הסדרה — MACD, חיתוכי EMA,
   `runBacktest` — קורא אינדקסים מוקדמים שנושאים מידע קדימה.

**קיימת מימוש שני, נכון, שאף בוט לא משתמש בו** —
`packages/engine/src/utils/advancedTechnicalAnalysis.ts:204-217` — שם ה-SMA
נכתב ב-`ema[period-1]`, האיברים לפניו `NaN`, והרקורסיה מתחילה מ-`i = period`.
כלומר יש בקוד שני מימושים של אותה פונקציה שאינם מסכימים.

## 2. ✅ Path — שער ה-RR הופך את רכיב ה-breakout לחצי-מת

**מאומת מספרית.** עם `tpRangeMult = 1.0`, `minRR = 1.2`, כניסה ב-`H + d`,
`SL = mid`:

```
RR = (range − d) / (range/2 + d) ≥ 1.2  ⟹  d ≤ 0.1818 · range
```

| d / range | RR | תוצאה | נק' breakout |
|---|---|---|---|
| 0.00 | 2.000 | ✅ | 0.0 / 30 |
| 0.10 | 1.500 | ✅ | 6.0 / 30 |
| **0.1818** | **1.200** | ✅ גבול | **10.9 / 30** |
| 0.20 | 1.143 | ❌ RR_BELOW_MIN | 12.0 |
| 0.50 | 0.500 | ❌ | 30.0 |

שתי מסקנות הדוח מאומתות:

1. **`maxExtensionRangeMult = 0.5` נבלע.** הבדיקה שלו (`prev4hRange.ts:219`)
   רצה *לפני* בדיקת ה-RR (`:233`), ולכן היא כן נגישה — אבל רק בטווח `d > 0.5`
   שגם ה-RR היה דוחה. היא לא קוד מת, היא **מיותרת**.
2. **רכיב ה-breakout מתוגמל הפוך.** `clamp01(d / (range·0.5)) · 30`
   (`:238`) מגיע למקסימום ב-`d = 0.5·range` — אזור שה-RR תמיד דוחה. בטווח
   הכשיר הוא נותן **0–10.9 מתוך 30**.

הביטחון המקסימלי האפקטיבי הוא `40 + 10.9 + 20 + 10 = 80.9`, והסף הוא 55 —
כלומר צריך 15 נקודות מ-trend+range+breakout. הבוט **כן** יורה (מדידה חיה כרגע:
2 פוזיציות פתוחות, 2 `willExecute`), אבל טווח הפעולה צר.

### 🔧 תיקון מוצע (P2)

ליישר את סקאלת ה-breakout לטווח שהשער מתיר — `clamp01(d / (range · 0.18)) · 30`
— כך ששני המנגנונים מושכים לאותו כיוון. `maxExtensionRangeMult` יורד ל-0.18
או מוסר. **זה שינוי אסטרטגיה**, דורש אישור.
